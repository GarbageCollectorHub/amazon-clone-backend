# Проверка IP и rate limiting после Publish

Локальные тесты `ForwardedHeadersTests` проверяют middleware с настройками проекта,
но не конфигурацию IIS/Azure. Эту проверку повторяем после смены хостинга или proxy.

## Что проверяем

- Login разрешает 5 запросов в минуту на IP, шестой получает 429.
- Произвольный `X-Forwarded-For` не позволяет обойти лимит.
- Два посетителя с разными публичными IP не делят один счётчик proxy.

## Порядок

1. Опубликовать текущую сборку. Вход с проверяемого IP не использовать минимум минуту.
2. Из корня репозитория выполнить:

   ```powershell
   .\scripts\Test-DeployedRateLimit.ps1 -BaseUri https://amzn-backend.azurewebsites.net/
   ```

   Первые 5 пустых запросов должны вернуть 400, следующий - 429. Два запроса
   с подставленными IP тоже должны вернуть 429. Пустое тело отклоняет валидация DTO:
   пользователи не создаются, пароль не проверяется. На минуту тест расходует лимит входа
   для текущего публичного IP, в том числе других людей за тем же NAT.

3. Пока первый IP ограничен, из другой сети выполнить:

   ```powershell
   .\scripts\Test-DeployedRateLimit.ps1 -BaseUri https://amzn-backend.azurewebsites.net/ -Mode CheckSeparateClient
   ```

   Ожидается 400, не 429. Подойдёт второй компьютер через мобильный интернет.
   Другая вкладка или инкогнито не меняют публичный IP. Если прошло больше минуты,
   первый счётчик уже мог сброситься - такой результат не доказывает разделение клиентов.

## Как понимать результат

Если шестой запрос вернул 400, сначала проверяем опубликованную версию и политику Login.
Если второй IP получил 429, исключаем его собственный активный лимит и только затем
проверяем RemoteIpAddress/proxy. Один ответ 429 сам по себе не доказывает ошибку forwarded headers.

Для Windows App Service используем опубликованный hostingModel как исходную точку диагностики.
Не очищаем KnownProxies/KnownNetworks и не включаем доверие всем forwarders ради прохождения теста.
Не берём первый адрес X-Forwarded-For вручную: его может прислать клиент.

Эта проверка подтверждает наблюдаемое разделение счётчиков между двумя сетями,
но не показывает точное значение RemoteIpAddress. Для точного адреса при необходимости
понадобится ограниченная диагностика приложения. Публичный endpoint для этого не добавляем.

## Квота изображений перед Publish

1. Проверьте, что строка подключения для EF указывает на нужную БД. Примените миграцию
   `AddImageUploadUsage` через `dotnet ef database update` до публикации новой сборки.
2. Если нужен другой лимит, задайте `ImageUploads__MonthlyLimitMiB` в App Service.
   Без переопределения приложение использует 500 МиБ на UTC-месяц.
3. После публикации проверьте, что существующие изображения открываются. При необходимости
   проверьте одну небольшую тестовую загрузку. Не исчерпывайте квоту на опубликованном демо:
   граничные и параллельные запросы проверяются на LocalDB.
