# Decisions

Здесь фиксируем решения, которые влияют на поведение проекта, и причины их выбора.

Ориентир разработки - production-like поведение с понятными проверками и тестами,
но без дополнительных механизмов и инфраструктуры, пока для них нет конкретной задачи.

## API и MVC

- **Один backend, два интерфейса:** REST API обслуживает отдельный React storefront,
  MVC даёт продавцам управление своими товарами, а администраторам - каталогом.
  Контроллеры работают через сервисы и репозитории; отдельный backend для MVC не нужен.

- **Общая JWT-аутентификация:** API и MVC используют один JWT handler. Явный Authorization
  имеет приоритет над `amzn_access`. MVC хранит токены в HttpOnly-cookie с SameSite=Lax,
  а формы изменения данных используют antiforgery. Доступ продавца проверяется по SellerId,
  а не только по наличию кнопки во view.

- **Refresh-токены ротируются:** в БД сохраняем SHA-256 хеш, не исходный токен.
  Отзыв старого токена и выпуск нового выполняются в одной транзакции; условный UPDATE
  позволяет использовать старый токен только один раз. Отозванные записи сразу не удаляем.

- **Валидация и ошибки:** форму/DTO проверяют DataAnnotations, бизнес-проверки остаются
  в сервисах, целостность данных защищает БД. MVC показывает ошибки через ModelState
  и validation spans. API возвращает `ApiErrorResponse` с code, message и traceId;
  технические детали внутренних ошибок остаются в логах.

- **Общие ограничения:** значения для форм, DTO, сервисов и конфигурации EF Core
  сгруппированы по назначению в `Shared/Limits`. Если сообщение описывает границу,
  оно берёт её из атрибута валидации или той же константы. Разные правила не объединяем:
  например, лимит email при входе отличается от регистрации, а длина имени бренда
  в форме отличается от размера столбца. При переносе действующие правила и схема БД не меняются.
  Подпись и проверка JWT используют один способ чтения и проверки ключа.

- **Лимиты входа разделены:** login - 5 запросов в минуту на IP, регистрация - 3 за 10 минут,
  refresh - 30 в минуту. MVC и API делят счётчик одной операции, но не расходуют лимиты друг друга
  или корзины. MVC-формы регистрации и изменений каталога получают HTML 429, login и API - JSON;
  Retry-After подсказывает время ожидания. Лимиты считают все запросы, не только неудачные.
  IP берём из RemoteIpAddress; за proxy корректность адреса зависит от доверенных ForwardedHeaders.

- **Forwarded headers не считаем доверенными автоматически:** оставляем проверку proxy,
  не читаем первый X-Forwarded-For вручную. Локальные тесты проверяют обработку цепочки
  и разделение лимитов; проверку опубликованного IIS/Azure выполняем отдельно
  по [инструкции](deployment-checks.md).

## Данные и каталог

- **SQL Server и EF Core:** локальная БД и Azure SQL используют один provider и миграции.
  При пробуждении Azure SQL повторяем открытие соединения, не весь бизнес-сценарий,
  чтобы не повторять внешние операции вроде загрузки изображения.

- **Оценки и отзывы:** на пару ProductId/UserId разрешена одна оценка и один отзыв.
  Изменения выполняются в транзакции с блокировкой товара `UPDLOCK, ROWLOCK`, затем
  пересчитываются RatingSum/RatingCount. Это защищает агрегаты от параллельных обновлений.
  Продавец не может оценивать свой товар или оставлять на него отзыв.

- **Каталог включает подкатегории:** фильтр категории использует всю её ветку.
  Список доступных брендов также ограничен этой веткой. Фильтрация, сортировка и пагинация
  товаров выполняются в БД; preview ответов Q&A ограничивается в запросе, не после загрузки всех ответов.
  Формы товара и фильтры цены используют общий максимум 1 000 000 за единицу товара.

- **Рейтинговые подборки главной зависят от данных:** учитываем наличие товара и среднюю оценку строго выше 2.5.
  Количество товаров и оценок для выбора категорий считаем по всей ветке; ограниченные
  подборки товаров загружаем из БД. Поэтому товары без оценок не заполняют эти секции.

- **Заказ хранит снимок товара:** название, бренд, цену и ссылку на главное изображение
  копируем в OrderItem. При удалении товара главное изображение в Blob сохраняем,
  поскольку на него могут ссылаться заказы; галерею удаляем отдельно.

## Изображения и запуск

- **Автотесты не используют облако:** xUnit проверяет правила изображений, отказы загрузки,
  forwarded headers и лимиты запросов. HTTP-стенд TestHost использует реальные политики,
  их атрибуты на методах контроллеров и Razor-ответ 429, но заменяет бизнес-обработчики.
  Размер multipart проверяем на настоящем Kestrel с фильтрами размера из методов приложения. Конфигурацию создаём в памяти,
  секреты не читаем. Авторизацию endpoint, запись в настоящий Azure Blob и настройки IIS/Azure
  эти стенды не проверяют. Отдельные тесты квоты на LocalDB применяют миграции к временным БД
  и проверяют сохранение счётчика, границу квоты, новый месяц и параллельные запросы.

- **Blob и БД не образуют общую транзакцию:** при ошибке создания/редактирования товара
  новые файлы удаляем best-effort. Удаление заменённых файлов делаем после сохранения БД.
  Ошибки очистки логируем; это компенсация, а не гарантия атомарности.

- **Допустимы JPEG (.jpg/.jpeg), PNG и WebP:** общий `ImageFileRules` проверяет расширение,
  Content-Type и размер до 5 МиБ перед записью в Blob. Пустой Content-Type отклоняем,
  сигнатуру содержимого пока не проверяем. Конструктор storage-сервиса не делает сетевых вызовов,
  поэтому недоступность Azure не мешает открыть каталог.

- **Ограничения загрузок:** создание/редактирование товара и создание категории имеют
  общий лимит 10 POST в минуту на аккаунт и 25 МиБ на весь запрос, включая multipart-данные.
  Редактирование без файлов тоже считается. Все 11 файлов по 5 МиБ за раз не помещаются.
  Размер файла, размер запроса и число фото в галерее заданы в `Shared/Limits/ImageUploadLimits.cs`.
  Формы, контроллеры и сервисы используют эти константы, а Razor передаёт размер файла и лимит галереи
  в JavaScript через `data-*`.
  Создание брендов и акций делит отдельный лимит: 10 POST в минуту на аккаунт.
  Эти счётчики живут в памяти процесса и ограничивают частоту, а не общий объём данных.

- **Общая месячная квота:** `ImageUploads:MonthlyLimitMiB` по умолчанию равна 500 МиБ.
  Перед записью каждого проверенного файла резервируем его размер в SQL. Транзакция блокирует
  запись текущего UTC-месяца, чтобы параллельные запросы не могли потратить один остаток дважды.
  После перезапуска счётчик сохраняется, в новом месяце используется новая запись.
  Ошибка Blob, удаление файла и откат сохранения товара не возвращают байты: загрузка могла уже
  пройти. Если SQL недоступен, запись в Blob не начинаем. Квота не ограничивает накопленный объём,
  чтение или число операций Blob и не является денежным лимитом Azure.

- **Аварийное отключение:** `ImageUploads:Enabled=false` запрещает новые загрузки,
  но не чтение и удаление. В Azure используем `ImageUploads__Enabled`.
  Прямое чтение публичных изображений из Blob не проходит через лимиты приложения.

- **Фоновые проверки акций:** при `Promotions:EnablePeriodicChecks=false` worker проверяет
  акции только при старте, чтобы не будить serverless-БД каждую минуту. При true проверка
  повторяется раз в минуту. В startup-only режиме время само по себе не запускает обновление акций.

- **Настройки развёртывания:** секреты не храним в Git. Для локального запуска используем
  игнорируемый `appsettings-Secrets.json`, для Azure - настройки приложения.
  Swagger включается отдельной настройкой `Swagger:Enabled`, независимо от Development,
  чтобы API можно было посмотреть в опубликованном демо.
